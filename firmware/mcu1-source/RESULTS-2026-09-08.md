## Recovery status

Before this source trial, four-second dial-held physical MCU1 bootloader entry and a
stock restoration were verified; the user confirmed audio, dial and display healthy.
After source execution, the user's first physical recovery attempt produced no visible
1038 HID or present Windows PnP device. A repeat power cycle and the visible power/display
state have been requested. Post-source physical recovery and diagnostic v2 restoration
are not yet verified. Source execution after the loader's warm handoff passed; reliable
cold boot has not been established. No additional image write has been attempted since.

Subsequent user-confirmed checks also produced no visible 1038/1FC9 USB device:
repeat four-second hold, ten seconds fully disconnected followed by ordinary USB1
power-on, adding USB2, and a twelve-second hold. Windows reported no matching present
PnP device or failed USB device in the inspected inventory. The screen remained dark,
but the user heard the headset's connection sound, suggesting the radio side remains
active. This does not establish that MCU1 is executing normally. The purpose of GPIO0_20,
set in the bootloader's long-hold branch, is not yet proven; its earlier description as
a power-control GPIO was an inference, not an established board mapping.

The user proposed opening the device for SWD. Direct read-only MCU1 inspection is now
the next recovery step. USB-only recovery cannot currently be completed. Do not mark
milestone A complete or assert that the bootloader is intact without a new readback.

## SWD inspection sequence

1. Identify the actual board revision and MCU1 pads against the FCC photographs. Use
   the LPC5528 MCU1 pads, not LPC5516 MCU2. The photographed labels include MCU1_SWCLK,
   MCU1_SWDIO, MCU1_RST, GND and VDD_1V8. Do not infer connector pin order from these names.
2. With a suitable probe and meter, establish ground and measure the target reference
   voltage. Confirm the probe supports it. Avoid enabling probe-supplied target power.
3. Attach without programming, unlock, recovery/mass erase, or automatic download.
   If debugging is locked, stop and inspect the reported state rather than accepting
   an erase prompt. Begin with a normal attach; use connect-under-reset only if needed.
4. Record target identity, PC/SP, reset/fault state, and clock/GPIO/USB configuration.
   Read accessible MCU1 flash before altering it. Compare [0,0xC000) with the boot
   capture, [0xC000,0x51BAC) with this source image, and reserved partitions with the
   historical tail. Loader-owned metadata may legitimately differ.
5. Diagnose cold startup from reset and whether the physical dial reaches the sampled
   recovery signal. Preserve evidence, then restore diagnostic v2 only within the
   application envelope using a verified programming method. Bootloader/factory writes
   are not part of this recovery plan.

Probe model, voltage compatibility and the actual board connections are pending.

## Remaining milestone A work

Software bootloader entry, persistent fault evidence, trace retrieval and broader
reliability testing remain incomplete. Current diagnostics support identity and
bounded code reads; fault status is a non-persistent field. This first build provides
no audio, dial, display or MCU2/DSP startup. No stock application functions are called.

MCU2/DSP images were not replaced. Bootloader and factory storage were outside the
host application's permitted write envelope; loader-owned metadata changes follow
the existing update procedure.
